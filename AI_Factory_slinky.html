AI Factory: Slurm–Kubernetes Integration with Slinky Slurm Bridge

Project report · HPC Technologies Group, C-DAC Pune · November 2026

Status: research, study and testing phase

Summary

An AI Factory needs HPC-grade scheduling for model training and cloud-native orchestration for serving models. This project studied how to run both on one cluster without replacing the Slurm scheduler already in use.

We evaluated the open-source Slinky framework from SchedMD, compared its two models (Slurm Operator and Slurm Bridge), and selected Slurm Bridge. On a small testbed we tested two workflows: a training job submitted through Slurm, and an inference service scheduled through the Bridge and served by Kubernetes. Both worked. The tests also showed limits we still need to resolve, mainly whole-node allocation per pod, CPU isolation and GPU visibility inside pods.

Why integration is needed

An AI Factory covers the full AI lifecycle on shared compute: data preparation, training, experiment tracking, model registry, deployment, inference and monitoring. Slurm and Kubernetes each cover part of it.

SlurmKubernetes
StrengthsMulti-node jobs, MPI and GPU-aware scheduling, topology awareness, gang scheduling, queues, fair-share, reservations, accountingDeclarative containers, service exposure, health probes, auto-restart, autoscaling, RBAC, a large tooling ecosystem
GapsBuilt around allocated jobs. No native persistent serving, REST APIs, dashboards or model registryNot MPI-aware, no HPC topology awareness, no fair-share or batch queue semantics, limited accounting

Running both side by side means two schedulers competing for the same nodes. The aim is to keep Slurm as the single resource allocator and let Kubernetes place pods on what Slurm allocates.

Slinky and the choice of Slurm Bridge

Slinky offers two components. The Slurm Operator runs and manages Slurm inside Kubernetes. The Slurm Bridge connects Kubernetes to an existing Slurm cluster, so pods are scheduled using Slurm resource allocations.

The AI Factory already has a working Slurm cluster, so we selected Slurm Bridge. It reuses Slurm’s scheduling policies, runs native Kubernetes applications, and needs no cluster replacement.

Architecture

A pod request moves through three layers, and the allocation result returns the same way.

  1. Kubernetes control plane. The API server accepts the pod YAML. An admission webhook applies the Bridge configuration, such as schedulerName.
  2. Slurm Bridge. The Bridge scheduler handles pending pods and requests Slurm allocations. State coordination tracks the pod-to-job mapping and cleanup.
  3. Existing Slurm cluster. The controller (slurmctld) applies policies and partitions through the Slurm REST API (slurmrestd). Compute nodes run slurmd and kubelet.

Slurm uses two partitions, standard and slurm-bridge. Kubernetes runs on kubeadm with containerd and Flannel. Pods use slurm-bridge-scheduler, and Slurm allocations are evaluated together with DRA (Dynamic Resource Allocation).

Implementation

  1. Configure the Slurm cluster: slurmctld, slurmd, compute nodes and the slurm-bridge partition.
  2. Deploy Kubernetes: control plane, workers, containerd and CNI networking.
  3. Enable the Slurm REST API with authentication and connectivity.
  4. Install the Slinky Slurm Bridge scheduler and admission components with Helm.
  5. Align schedulerName, partitions, node taints, CPU/GPU resources and DRA.
  6. Submit a test pod and check Kubernetes placement against the Slurm allocation.

The main setup challenges were aligning Kubernetes scheduling with Slurm partitions, making CPU/GPU allocation efficient, and securing communication between the two systems. These were handled with a dedicated Bridge scheduler setup, DRA configuration, and authenticated slurmrestd access with end-to-end pod-to-node mapping checks.

Workflows

Training through Slurm

The user submits sbatch train.sbatch with CPU, GPU, memory and time needs. Slurm checks partitions, priorities and policies, allocates compute nodes, and the training script runs there. The model files are saved to storage and Slurm releases the resources.

Inference through the Bridge

The user submits pod YAML with the Bridge schedulerName. The Bridge reads the pod’s requirements and requests a Slurm allocation through slurmrestd. Slurm allocates node(s) under its policies, the Bridge binds the pod to them, and the kubelet starts the serving container. Slurm allocates resources, the Bridge coordinates placement, and Kubernetes manages the container lifecycle.

The design targets LLM serving, for example with vLLM or TGI. The tests used a lightweight model, as described below.

Early tests showed the Bridge reserving a whole compute node for one pod, even for a small request such as 2 CPUs on a 16-CPU node. We diagnosed a CPU DRA allocation mismatch, aligned the pod and Slurm node allocation, and validated the admission and scheduling flow. The target is shared, granular allocation, where several pods use one node.

Open items. Whole-node allocation per pod was still observed. CPU DRA isolation and GPU device visibility need further work. Multi-replica scaling is limited by node availability on a two-compute-node testbed. The results show that the approach works, not how it performs at scale.

Slinky Slurm Bridge is a workable way to let Slurm and Kubernetes share one cluster, with Slurm as the single allocator. The next step is to close the open items above, then extend testing toward larger node counts, fault tolerance, GPU sharing and multi-tenant use.
